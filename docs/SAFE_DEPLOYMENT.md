# النشر الآمن بدون حذف قاعدة البيانات

## السبب الجذري

بعض أدوات رفع ZIP تعمل كمزامنة كاملة: أي ملف موجود في مجلد التطبيق وغير موجود في الحزمة الجديدة يُحذف. لذلك لا يجوز إبقاء `.env` أو `database/db.json` أو `database/legacy-password-vault.key` داخل مجلد الإصدار القابل للاستبدال.

## التهيئة لمرة واحدة — أول رفع لهذا الإصدار

في شاشة الرفع الأولى فقط، استخدم أيقونة سلة المهملات الظاهرة بجانب عناصر الحذف لإلغاء حذف هذه الملفات الثلاثة:

```text
.env
database/db.json
database/legacy-password-vault.key
```

ثم ارفع الحزمة الكاملة وأعد تشغيل التطبيق. عند أول تشغيل، ينسخ التطبيق الملفات القديمة تلقائيًا — من دون حذفها — إلى المجلد الشقيق الدائم:

```text
../schedule-private/
```

بعد نجاح التشغيل وتسجيل الدخول، نفّذ أمر التحقق والنسخ الاحتياطي:

```bash
npm run protect:data
```

ينشئ الأمر نسخة استرجاع سريعة ونسخة احتياطية مؤرخة وبصمات SHA-256، ويمكن تشغيله بأمان مرة أخرى لاحقًا. بعد التأكد، تستطيع أداة الرفع حذف النسخ القديمة داخل مجلد البرنامج في الرفعات اللاحقة؛ التطبيق لن يعتمد عليها بعد الآن.

إذا كانت منصة الاستضافة تستبدل المجلد الأب أيضًا، فلا تستخدم المسار الافتراضي. أنشئ مسار تخزين دائم خارج نطاق الاستبدال وعيّنه في إعدادات بيئة الاستضافة قبل التشغيل:

```text
SCHEDULE_PRIVATE_DIR=/absolute/persistent/path/schedule-private
```

بعد نجاح الأمر، أعد تشغيل التطبيق مرة واحدة وتحقق من تسجيل الدخول وعدد السجلات. من هذه اللحظة يمكن استبدال مجلد الكود؛ قاعدة البيانات والأسرار أصبحت خارجه.

## قواعد أمان

- لا ترفع `.env` أو قاعدة البيانات أو مفتاح الخزنة داخل ZIP أو مستودع عام.
- لا توافق على حذف الملفات الثلاثة في **أول رفع لهذا الإصدار**. الكود الجديد يحتاج رؤيتها مرة واحدة لينسخها إلى التخزين الدائم.
- في الإنتاج يرفض التطبيق أي `SCHEDULE_PRIVATE_DIR` يقع داخل مجلد البرنامج، حتى لا يعود الخطر بصمت.
- لا تستخدم `migrate:firestore:replace` على قاعدة إنتاج.
- الكتابة المحلية أصبحت ذرّية، ويُحفظ `db.json.backup` قبل كل تغيير ناجح، ويُستعاد تلقائيًا إذا اختفى الملف الرئيسي.
