السبب الجذري:
- التصدير الكامل السابق كان طلب HTTP واحداً: يقرأ Firestore كاملاً، ثم يفحص subcollections لكل مستند، ثم يبني JSON وSHA-256 وgzip قبل أن يبدأ أي تنزيل. مع قاعدة كبيرة يصبح المتصفح بلا تقدم مرئي، ويمكن أن ينتهي طلب Cloud Run قبل إنشاء الملف.
- الجزء الأبطأ كان listCollections لكل مستند، رغم أن بنية SCHEDULE الدائمة الحالية مسطحة عدا legacyArchive/{table}/rows.

الحل:
- استبدال التصدير الطويل بمهمة تصدير دائمة قابلة للاستكمال، مخزنة في _systemExportJobs (ومستثناة من النسخة نفسها).
- قراءة Firestore على صفحات صغيرة مع cursor ونقطة تقدم محفوظة بعد كل دفعة.
- اكتشاف جميع top-level collections تلقائياً + أرشيف legacyArchive/rows المتداخل بالكامل.
- تخزين staging مضغوط، ثم بناء ملف gzip النهائي مرة واحدة وحفظه كأجزاء داخل مهمة التصدير.
- التنزيل النهائي لا يعيد قراءة قاعدة النظام؛ يرسل الملف الجاهز فقط.
- إذا أُغلقت الصفحة أو انقطع الاتصال، لا يضيع ما تم جمعه؛ عند الرجوع يظهر نفس التقدم ويمكن استكماله.
- واجهة الخزنة تعرض نسبة التقدم، عدد السجلات، المراحل، الحجم، SHA-256، وزر تنزيل مستقل بعد الجاهزية.
- أثناء وجود تصدير قيد التنفيذ تُقفل عمليات الاستيراد/التصفير/التراجع لمنع أخذ نسخة غير متسقة أثناء تغيير قاعدة النظام.
