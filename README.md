# SCHEDULE 2026 — Academic Workspace

إعادة بناء حديثة لنظام **SCHEDULE** مع المحافظة على منطق النظام القديم وبياناته وصلاحياته، مع واجهة عربية RTL هادئة تضع العمل اليومي في الواجهة وتخفي التعقيد داخل طبقات القرار والباك إند.

## النشر على Google AI Studio / Cloud Run

الحزمة الحالية مهيأة حتى لا تتكرر مشكلة حجم ملف البيانات أو الكتابة داخل مجلد التطبيق:

- Snapshot البيانات الحقيقي مضغوط داخل `database/db.json.gz` بدل ملف JSON بحجم يقارب 15MB.
- الخادم وMigration يقرآن `.gz` مباشرة باستخدام `zlib`؛ لا حاجة لفك الضغط داخل مجلد التطبيق.
- عند اكتشاف Cloud Run، يتحول `DATA_MODE=demo` تلقائياً إلى **Firestore** لأن تخزين الحاوية مؤقت وغير مناسب لبيانات التشغيل.
- أي ملفات Runtime مساعدة تستخدم `/tmp/schedule-private` على Cloud Run فقط؛ البيانات الدائمة تبقى في Firestore.
- لا تضع `node_modules` داخل ZIP. منصة البناء تنفذ التثبيت والبناء من `package.json`.

للتأكد من سلامة حزمة النشر بعد فكها:

```bash
npm run audit:deploy
```

ثم في بيئة البناء:

```bash
npm ci
npm run build
npm start
```

## Firestore

الإعداد المقصود للإنتاج:

```env
DATA_MODE=firestore
FIREBASE_PROJECT_ID=your-project-id
AUTO_IMPORT_LEGACY_DATA=true
```

إذا كان Firestore فارغاً، ينتظر الخادم اكتمال استيراد نسخة Legacy المضغوطة قبل قبول أول Login، ثم يتحقق من Counts ويسجل Marker في `_meta/legacyImport`.

للاستيراد اليدوي:

```bash
npm run migrate:firestore
```

ولإعادة تعبئة **قاعدة اختبار فقط** بصورة مقصودة:

```bash
npm run migrate:firestore:replace
```

الوضع الثاني مدمر للـCollections المستهدفة، فلا يستخدم على قاعدة إنتاج تحتوي بيانات جديدة.

## التشغيل المحلي

يمكن إبقاء:

```env
DATA_MODE=demo
```

في التشغيل المحلي أو الاستضافة التقليدية ذات التخزين الدائم. عند أول تشغيل، يفك التطبيق `db.json.gz` مرة واحدة إلى مجلد Runtime خاص خارج مجلد الإصدار ثم يستخدم الكتابة الذرية والنسخة الاحتياطية.

```bash
npm install
npm run dev
```

بيانات دخول المدير الموجودة في النسخة المهاجرة هي بيانات النظام القديم نفسها. لا تحفظ بيانات الدخول في مستودع عام.

## حماية البيانات في الاستضافة التقليدية

على cPanel أو أي استضافة يكون فيها مجلد دائم خارج Release، عيّن مثلاً:

```env
SCHEDULE_PRIVATE_DIR=/absolute/persistent/path/schedule-private
```

ثم نفّذ مرة واحدة:

```bash
npm run protect:data
```

Cloud Run لا يحتاج هذا الأسلوب للبيانات التشغيلية؛ Firestore هو مصدر الحقيقة الدائم هناك.

## التحقق

قبل رفع حزمة المصدر النظيفة، وقبل تثبيت `node_modules`:

```bash

```

وفي بيئة التطوير/البناء بعد `npm ci`:

```bash
npm run lint

npm run build
```

أو شغّل الاختبارات منفردة:

```bash
npm run test:behavior
npm run test:data
npm run test:credentials

```

## ملاحظات الواجهة

الواجهة الحالية مبنية على مبدأ: **البساطة أمام المستخدم، التعقيد خلفها**. لذلك شاشة الجدول تعرض حالة واحدة مختصرة ومركز قرار واحد، بينما المقارنة، بصمة القسم، المحاكاة، الذاكرة، شبكة الأمان، الطوارئ وتحليل العدالة ما زالت موجودة داخل مركز القرار ولم تُحذف أي وظيفة بسبب التبسيط البصري.

## الخصوصية

`database/db.json.gz` و`database/legacy-password-vault.key` يحتويان بيانات خاصة. الحزمة المرسلة لصاحب النظام قد تتضمنهما للنقل الأول، لكن لا ينبغي نشرهما في مستودع عام أو مشاركتهما خارج بيئة النظام.


### وضع التشغيل
على Cloud Run يفرض التطبيق `NODE_ENV=production` تلقائياً حتى يخدم ناتج البناء المترجم من `dist`. في cPanel أو Node التقليدي عيّن `NODE_ENV=production` في بيئة الاستضافة قبل تشغيل التطبيق.
